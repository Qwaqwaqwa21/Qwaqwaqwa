# Семейный бот задач с интеграцией в Яндекс Календарь

Статус: **проектирование завершено, решения зафиксированы**. Кода пока нет.

## 1. Что решаем

Дела по семье живут в головах и в чатах: «купи корм», «забери из школы», «в 18:00 СДЭК».
Часть теряется, часть делают дважды, никто не видит общей картины на день.

Бот принимает дела текстом, привязывает их к **исполнителю** и **времени**, кладёт в общий
семейный календарь и сам напоминает нужному человеку в нужный момент.

Три обязательных атрибута любого дела: **время — исполнитель — дело**.

Сейчас в семье двое взрослых, состав будет расширяться — модель данных с самого начала
рассчитана на произвольное число участников.

## 2. Ключевое ограничение платформы

У Яндекс Календаря **нет публичного REST API**. Единственный поддерживаемый путь —
**CalDAV** (`https://caldav.yandex.ru`) с **паролем приложения** из Яндекс ID
(раздел Безопасность → Пароли приложений → Календарь CalDAV).

Из этого следует:

| Ограничение | Следствие для архитектуры |
|---|---|
| Нет OAuth, только пароль приложения | Нельзя «подключить календарь в один клик». Пароль = полный доступ к календарю, хранить только в зашифрованном виде |
| Нет вебхуков | Изменения, сделанные прямо в календаре, видим только опросом (polling по `sync-token`/ETag, раз в 5–15 мин) |
| Настройки уведомлений не наследуются при шаринге | Напоминания из общего календаря **не дойдут** до членов семьи автоматически (см. §4) |

## 3. Схема аккаунтов и календарей

**Решение: один семейный Яндекс-аккаунт.**

- Бот подключается к нему по CalDAV с паролем приложения.
- Внутри аккаунта — **отдельный календарь на каждого члена семьи**, свой цвет.
- Календари расшарены остальным по их Яндекс-адресам. Каждый принимает приглашение один
  раз, после чего видит семейный слой **у себя в личном аккаунте**, без переключения
  аккаунтов, включая мобильное приложение.

Почему не «у каждого свой аккаунт»: пароль приложения даёт полный доступ к календарю
человека, а настройка неподъёмна для тех, кто добавится позже.

Отдельного календаря «Общее» нет: у каждого дела всегда есть конкретный ответственный
(см. §6). Совместные дела попадают в календарь **каждого** участника.

## 4. Уведомления — главное архитектурное решение

Яндекс при выдаче доступа к календарю **не передаёт приглашённым настройки уведомлений**.
Напоминание внутри события принадлежит владельцу календаря, то есть уйдёт на семейный
аккаунт, а не исполнителю. Поэтому календарь **не может** быть каналом доставки.

Раскладываем роли:

- **Бот — канал уведомлений.** Знает исполнителя и время, шлёт пуш в личку с кнопкой
  «Готово». Адресно, мгновенно, не зависит от того, кто чей календарь принял.
- **Яндекс Календарь — витрина и источник правды.** Открыть телефон и увидеть неделю
  семьи целиком; синхронизация на все устройства; данные переживут падение бота.

**Гибрид для важных дел.** У дела есть флаг «важное» (врач, школа, поезд, самолёт). Для
таких бот дополнительно добавляет исполнителя **участником события** (`ATTENDEE` по email).
Событие падает в личный календарь человека, и срабатывают уже **его** напоминания.
Цена — письмо-приглашение с кнопками «Пойду / Может быть / Не пойду», поэтому режим
включается только по флагу, а не на каждое «вынести мусор».

**Страховка.** `VALARM` внутрь события пишем всегда — если бот лежит, напоминание
хотя бы сработает у владельца календаря.

## 5. Модель данных

Дело живёт в двух местах: в своей БД (статусы, авторство, история — в iCalendar это не
положить) и как событие в календаре. Связь через `UID` события.

### `members`

`id`, `telegram_id`, `name`, `aliases` (варианты имени для разбора текста),
`yandex_email` (для `ATTENDEE`), `calendar_url` (личный календарь внутри семейного
аккаунта), `role` (`adult` / `child`), `active`.

### `tasks`

| Поле | Обяз. | Описание |
|---|---|---|
| `id` | да | Внутренний ID |
| `title` | да | «Забрать посылку в СДЭК» |
| `date` | да | По умолчанию — сегодня |
| `time_start` | нет | Пусто → дело «на день», в календарь не пишем (см. §7) |
| `duration_min` | нет | По умолчанию 30 |
| `author_id` | авто | Кто поставил |
| `status` | авто | `new` / `done` / `cancelled` |
| `is_joint` | авто | Больше одного исполнителя (см. §5.1) |
| `important` | нет | Включает режим `ATTENDEE` из §4 |
| `rrule` | нет | Повтор («каждый вторник») — уходит в CalDAV как есть |
| `remind_before_min` | нет | По умолчанию 15 |
| `created_at` / `done_at` | авто | Для истории и статистики |

Исполнитель вынесен из `tasks` в отдельную таблицу — иначе совместные дела и передача
не ложатся на модель.

### `task_assignees`

`task_id`, `member_id`, `status` (`active` / `done` / `transferred`), `caldav_uid`,
`caldav_etag`, `done_at`.

Одна строка = одно дело у одного человека = **одно событие в его календаре**. У совместного
дела строк несколько, у обычного — одна.

### `task_transfers`

`task_id`, `from_member_id`, `to_member_id`, `status` (`pending` / `accepted` / `declined`),
`created_at`, `resolved_at`. Нужна для истории («кто на кого спихнул») и чтобы не потерять
запрос, если человек не ответил сразу.

### 5.1 Совместные дела

Дело, которое делают вместе: «в субботу в 12:00 разобрать кладовку — оба».

- В карточке подтверждения исполнителей можно отметить нескольких.
- Событие пишется **в календарь каждого** участника, отдельным `UID`, все связаны одним
  `task_id`. Так у каждого расписание полное и корректно ловятся конфликты по времени.
- Напоминание приходит всем участникам.
- «Готово» отмечается индивидуально. Пока отметились не все, бот показывает прогресс:
  `Готово: 1 из 2 (ждём Машу)`. Дело переходит в `done`, когда отметились все.
- В заголовке события у каждого — общий текст плюс пометка «вместе с ...», чтобы в календаре
  было видно, что дело не в одиночку.

### 5.2 Передача задачи

Сценарий: не могу — пусть сделает другой.

1. Исполнитель жмёт **«Передать»** под задачей (в напоминании, в `/my`, в карточке).
2. Выбирает, кому — кнопками из списка семьи.
3. Может добавить короткий комментарий («я на работе до 20»).
4. Адресату приходит запрос: `Ваня передаёт тебе: Забрать посылку, сегодня 18:00.
   «я на работе до 20». [✅ Беру] [❌ Не могу]`.
5. **Принял** → в `task_assignees` строка старого исполнителя переходит в `transferred`,
   его событие из календаря удаляется, создаётся событие в календаре нового. Напоминание
   перевешивается. Автор задачи и прежний исполнитель получают уведомление.
6. **Отказался** → задача остаётся на прежнем исполнителе, ему приходит отказ с комментарием.
7. **Не ответил** до момента напоминания → задача остаётся на прежнем, запрос гаснет,
   обоим приходит сообщение, что передача не состоялась.

Правила:

- Передавать может исполнитель или автор задачи. Ребёнок может **предложить** передачу
  взрослому, но не наоборот навязать.
- У совместного дела передаётся **своя доля**: уходит только та строка `task_assignees`,
  остальные участники остаются.
- Передать можно только незавершённую задачу.
- Повторная передача разрешена — история копится в `task_transfers`.

### Права

- **Взрослый** — ставит задачи кому угодно, передаёт свои.
- **Ребёнок** — ставит себе; другим — только как предложение, с подтверждением адресата.
- Регистрация закрытая: вход в семью только по одноразовому инвайт-коду. Иначе бот открыт
  всему Telegram.

## 6. Ввод задач

**Основной путь: свободный текст + разбор правилами.**
`«Маша завтра в 18:00 забрать посылку, 30 минут»` → `dateparser` для времени, справочник
имён семьи для исполнителя, остаток — название дела. Несколько имён подряд
(`«Маша и Ваня в субботу в 12:00 разобрать кладовку»`) → совместное дело.

**Карточка подтверждения обязательна** перед записью:

```
Маша · завтра, 18:00–18:30
Забрать посылку
[✅ Записать]  [✏️ Исправить]  [❌ Отмена]
```

Без неё кривой разбор будет мусорить в общем календаре.

**Запасной путь:** если разбор не уверен — пошаговый диалог кнопками
(дело → кто → когда → во сколько).

**Исполнитель обязателен.** Дел «кто-нибудь сделает» нет — если в тексте не нашлось имени,
бот спрашивает, кому. По умолчанию предлагает автора.

LLM-парсер — возможное улучшение позже (сложные формулировки, несколько дел в одном
сообщении). В MVP не нужен: правил хватает на большинство бытовых фраз, они быстрее,
бесплатны и предсказуемы.

## 7. Поведение бота

- **Утренняя сводка** (08:00, в общий чат): дела всех на сегодня одним сообщением,
  сгруппированы по людям.
- **Напоминание** за `remind_before_min` — лично исполнителю (всем участникам, если дело
  совместное), с кнопками «Готово» и «Передать».
- **Отметка о выполнении** → статус в БД + ✅ в заголовке события.
- **Проверка конфликтов**: если у исполнителя на это время уже что-то есть — предупредить
  на шаге подтверждения.
- **Обратная синхронизация**: событие подвинули или удалили в календаре — бот замечает при
  опросе и сообщает автору задачи.

**Дела без времени** держим только в боте и показываем в утренней сводке. В календарь как
all-day не пишем — они захламляют верх сетки и вытесняют реальные встречи.

**Часовой пояс** задаём явно (`TZID=Europe/Moscow`) в каждом событии, иначе время
поедет. Пока считаем, что вся семья в одном поясе; вынесено в конфиг одной строкой.

## 8. Безопасность

- Пароль приложения Яндекса — шифрование Fernet, ключ в переменной окружения, не в БД
  и не в репозитории.
- Токен бота — тоже из окружения.
- Закрытая регистрация по инвайт-коду, одноразовому и с истечением.
- Ребёнок не может менять чужие задачи.

## 9. Этапы

### MVP

1. Регистрация семьи по инвайт-коду, роли.
2. Создание задачи: текст с разбором + кнопочный запасной путь, карточка подтверждения.
3. Совместные дела (несколько исполнителей).
4. Запись в Яндекс Календарь через CalDAV (событие + `VALARM` + `TZID`), по событию на
   каждого исполнителя.
5. `/today` — что у семьи сегодня; `/my` — что у меня.
6. Напоминания в личку с кнопками «Готово» и «Передать».
7. Передача задачи с подтверждением адресата.
8. Утренняя сводка.

### Дальше

9. Флаг «важное» → `ATTENDEE` в личный календарь.
10. Повторяющиеся дела (`RRULE`).
11. Вечерний разбор (21:00) и перенос невыполненного.
12. Обратная синхронизация из календаря.
13. Голосовой ввод (распознавание → тот же разбор).
14. Статистика за месяц, теги/категории, чек-листы внутри дела.

## 10. Разработка и эксплуатация

- **Стек:** Python, `aiogram` (Telegram), `caldav` + `icalendar`, `APScheduler`
  (напоминания и сводки), SQLite.
- **Хостинг:** VPS ~200–300 ₽/мес. Постоянный процесс обязателен: напоминания срабатывают
  по времени, а правки в календаре видно только опросом — без работающего процесса
  некому проснуться. Домашний сервер или Raspberry Pi подойдут так же. Serverless
  (Yandex Cloud Functions + таймер) формально дешевле, но требует другой архитектуры:
  нет постоянного процесса, планировщик заменяется крон-триггером, состояние только в БД.
  Логика пишется независимо от способа запуска, чтобы переезд не был переписыванием.
- **Расположение в репозитории:** отдельный модуль `familybot/`. Основной проект
  (ГИС/каротаж) не затрагивается.

## 11. Зафиксированные решения

1. **Платформа — Telegram.**
2. **Один семейный Яндекс-аккаунт**, личные аккаунты не подключаем.
3. **Ввод — текст с разбором правилами**, кнопки как запасной путь. LLM — позже.
4. **Дела без времени** — только в боте, в календарь не пишем.
5. **Вечерний разбор** — нужен, но после MVP.
6. **Свободных дел «кто возьмёт» нет** — исполнитель обязателен всегда.
7. **Совместные дела и передача задачи** — в MVP.
8. **Вся семья в одном часовом поясе** (`Europe/Moscow` по умолчанию, меняется в конфиге).
9. **Хостинг — VPS.**
